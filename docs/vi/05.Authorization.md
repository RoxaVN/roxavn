## Giới thiệu về Policy

RoxaVN có cách tiếp cận kiểm soát quyền truy cập (authorization) khác biệt so với các framework truyền thống. Thay vì phải tự kiểm tra quyền trong từng hàm xử lý (controller/service), RoxaVN cho phép bạn định nghĩa các policy ngay tại khai báo API.

Nhờ vậy:

- **Backend** không cần viết lại các đoạn `if (!hasPermission) throw forbiddenException()` nữa, vì đã có `AuthorizeApiMiddleware` tự động kiểm tra.
- **Frontend** không cần tự xử lý quyền thủ công, mà chỉ cần dùng các tiện ích sẵn có như component `<IfCanAccessApi />` hoặc hook `useAuthorization()`.

Ví dụ trên Frontend:

```tsx
<IfCanAccessApi api={messageApi.getMany} children={<ListMessages />} />;
```

Đoạn code trên sẽ:

- Kiểm tra xem user hiện tại có quyền gọi API `messageApi.getMany` hay không.
- Nếu có quyền, component `<ListMessages />` sẽ được hiển thị.
- Nếu không có quyền, component đó sẽ không render — giúp giao diện tự động ẩn các phần không được phép truy cập.

### Định nghĩa policy trong API

Mỗi API trong RoxaVN có thể định nghĩa danh sách các policy kiểm tra quyền thông qua thuộc tính `authorization.policies`. Cấu trúc như sau:

```ts
authorization: {
  policies: Array<(context: PolicyContext) => Promise<boolean> | boolean>,
},
```

Trong đó:

- `context` là ngữ cảnh hiện tại, có kiểu là `PolicyContext` bao gồm thông tin người dùng, request khi gọi api.
- Mỗi phần tử trong mảng `policies` là một hàm trả về kết quả cho phép hay không.
- Khi có **ít nhất một policy hợp lệ**, user được phép truy cập API.
- Nếu **không có policy nào cho phép**, server sẽ tự động trả về lỗi **403 Forbidden** mà không cần viết thêm code.

## PolicyContext

`PolicyContext` cung cấp ngữ cảnh thực thi cho một Authorization Policy, bao gồm thông tin request, người dùng hiện tại và các công cụ hỗ trợ truy xuất resource hoặc kiểm tra quyền truy cập.

Thông qua `PolicyContext`, policy có thể kiểm tra quyền dựa trên dữ liệu request, trạng thái của resource và mối quan hệ giữa các resource mà không cần trực tiếp phụ thuộc vào tầng truy vấn dữ liệu.

### Interface

```ts
export interface PolicyContext<T = any> {
  request: T;
  user?: { id: string };
  $resolver: PolicyResolver;
}
```

| Property    | Type             | Description                                                                             |
| ----------- | ---------------- | --------------------------------------------------------------------------------------- |
| `request`   | `T`              | Dữ liệu request được truyền vào policy.                                                 |
| `user`      | `{ id: string }` | Thông tin người dùng hiện tại. Không tồn tại nếu request không có người dùng đăng nhập. |
| `$resolver` | `PolicyResolver` | Cung cấp các phương thức truy xuất resource, resource liên quan và kiểm tra permission. |

## PolicyResolver

`PolicyResolver` cung cấp các phương thức hỗ trợ policy truy xuất dữ liệu và kiểm tra quyền truy cập.

Resolver được khởi tạo với thông tin người dùng hiện tại. Các phương thức liên quan đến resource có thể được sử dụng độc lập với người dùng, trong khi `checkPermission` tự động sử dụng ID của người dùng đã được thiết lập.

### getResource()

Lấy một resource theo ID.

```ts
getResource<T extends Resource>(params: {
  resource: T;
  id: string;
}): Promise<InferResource<T> | null | undefined>
```

**Parameters:**

| Property   | Description             |
| ---------- | ----------------------- |
| `resource` | Resource cần truy xuất. |
| `id`       | ID của resource.        |

**Returns:**

- Resource tương ứng nếu tìm thấy.
- `null` hoặc `undefined` nếu không tìm thấy resource.

**Example:**

```ts
const workflow = await $resolver.getResource({
  resource: resources.Workflow,
  id: request.workflowId,
});

if (!workflow) {
  return false;
}

return workflow.createdBy === user?.id;
```

### findResource()

Tìm kiếm một resource theo các điều kiện tùy chỉnh.

```ts
findResource<T extends Resource>(params: {
  resource: T;
  condition: Partial<InferResource<T>>;
}): Promise<InferResource<T> | null | undefined>
```

**Parameters:**

| Property    | Description                      |
| ----------- | -------------------------------- |
| `resource`  | Resource cần tìm kiếm.           |
| `condition` | Các điều kiện tìm kiếm resource. |

**Returns:** Resource đầu tiên thỏa mãn điều kiện hoặc `null` / `undefined` nếu không tìm thấy.

**Example:**

```ts
const membership = await $resolver.findResource({
  resource: resources.ProjectMember,
  condition: {
    projectId: request.projectId,
    userId: user?.id,
  },
});

return !!membership;
```

### getRelatedResource()

Truy xuất resource liên quan thông qua một khóa tham chiếu từ resource nguồn.

```ts
getRelatedResource<S extends Resource, D extends Resource>(params: {
  source: S;
  sourceId: string;
  destination: D;
  destinationKey: keyof InferResource<S>;
}): Promise<InferResource<D> | null | undefined>
```

**Parameters:**

| Property         | Description                                                                |
| ---------------- | -------------------------------------------------------------------------- |
| `source`         | Resource nguồn.                                                            |
| `sourceId`       | ID của resource nguồn.                                                     |
| `destination`    | Resource đích cần truy xuất.                                               |
| `destinationKey` | Tên thuộc tính trên resource nguồn chứa khóa tham chiếu đến resource đích. |

**Returns:** Resource đích tương ứng hoặc `null` / `undefined` nếu không tìm thấy.

**Example:**

```ts
const project = await $resolver.getRelatedResource({
  source: resources.Task,
  sourceId: request.taskId,
  destination: resources.Project,
  destinationKey: 'projectId',
});

if (!project) {
  return false;
}

return project.ownerId === user?.id;
```

### checkPermission()

Kiểm tra người dùng hiện tại có permission trên một resource cụ thể hay không.

Hệ thống phân quyền của RoxaVN được thiết kế để giải quyết các bài toán như sau:

- Mỗi **module** trong RoxaVN có thể có **các chức vụ (role)** riêng biệt với **quyền (permission)** cụ thể để quản lý dữ liệu trong module đó.
  - Module `@roxavn/module-message` có role `Admin` với quyền _xem_, _sửa_, _xoá_ tất cả `Channel` và `Message`.
  - Module `@roxavn/module-project` có role `Admin` (chỉ cùng tên, khác id với role `Admin` của @roxavn/module-message) với quyền _xem_, _sửa_, _xoá_ tất cả `Project` và `Task`.

- Bên cạnh đó, trong từng **phạm vi nhỏ hơn** (như Channel, Project, ...), người dùng có thể có **role riêng biệt**.  
  → Ví dụ: trong channel “Tin tức về RoxaVN” (id = 1), người dùng có thể mang vai trò `ChannelAdmin` hoặc `ChannelModerator`, cho phép họ _xem_, _sửa_, _xoá_ tất cả `Message` thuộc riêng channel này.

```ts
checkPermission(params: {
  resourceType: string;
  resourceId: string;
  permission: string;
}): Promise<boolean>
```

**Parameters:**

| Property       | Description                                                                                                                                                                                    |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `resourceType` | Tên của tài nguyên được áp dụng quyền. Ví dụ: <br> - `@roxavn/module-message` cho role cấp module <br> - `channel` cho role cấp channel                                                        |
| `resourceId`   | ID của tài nguyên được áp dụng quyền. <br> - Với role module, `resourceId = '*'` (áp dụng cho toàn bộ module). <br> - Với role cấp channel, `resourceId` chính là ID của channel (ví dụ: `1`). |
| `permission`   | Permission cần kiểm tra.                                                                                                                                                                       |

**Returns:** `true` nếu người dùng có permission, ngược lại trả về `false`.

Nếu không có người dùng hiện tại (`user` không tồn tại), phương thức tự động trả về `false`.

**Example:**

```ts
return $resolver.checkPermission({
  resourceType: 'Project',
  resourceId: request.projectId,
  permission: 'UpdateProject',
});
```

## Ví dụ thực tế

### Kiểm tra quyền truy cập dựa trên resource

Policy cho phép người dùng truy cập workflow nếu họ là người tạo workflow.

```ts
const workflowOwnerPolicy = async ({
  request,
  user,
  $resolver,
}: PolicyContext<{ workflowId: string }>) => {
  const workflow = await $resolver.getResource({
    resource: resources.Workflow,
    id: request.workflowId,
  });

  return !!workflow && workflow.createdBy === user?.id;
};
```

### Kiểm tra quyền dựa trên resource liên quan

Policy cho phép người dùng cập nhật task nếu họ là chủ sở hữu project chứa task đó.

```ts
const projectOwnerPolicy = async ({
  request,
  user,
  $resolver,
}: PolicyContext<{ taskId: string }>) => {
  const project = await $resolver.getRelatedResource({
    source: resources.Task,
    sourceId: request.taskId,
    destination: resources.Project,
    destinationKey: 'projectId',
  });

  return !!project && project.ownerId === user?.id;
};
```

### Kết hợp nhiều điều kiện permission

Policy cho phép người dùng cập nhật workflow nếu họ có permission `UpdateWorkflow` trên workflow hoặc là người tạo workflow.

```ts
const workflowUpdatePolicy = async ({
  request,
  user,
  $resolver,
}: PolicyContext<{ workflowId: string }>) => {
  const workflow = await $resolver.getResource({
    resource: resources.Workflow,
    id: request.workflowId,
  });

  if (!workflow) {
    return false;
  }
  if (workflow.createdBy === user?.id) {
    return true;
  }

  return $resolver.checkPermission({
    resourceType: 'Workflow',
    resourceId: workflow.id,
    permission: 'UpdateWorkflow',
  });
};
```

## Triển khai dành riêng cho nền tảng

`PolicyResolver` cung cấp một API thống nhất cho cả Backend và Frontend. Tuy nhiên, cách triển khai các phương thức có thể khác nhau tùy thuộc vào môi trường thực thi. Mục tiêu là đảm bảo cùng một Authorization Policy có thể được sử dụng trên cả hai môi trường mà không cần quan tâm đến nguồn dữ liệu hoặc cách thức truy xuất dữ liệu.

### Backend

Trên Backend, `PolicyResolver` truy xuất dữ liệu trực tiếp từ database để đảm bảo kết quả kiểm tra quyền dựa trên dữ liệu thực tế.

| Method                 | Implementation                                                                               |
| ---------------------- | -------------------------------------------------------------------------------------------- |
| `findResource()`       | Truy vấn database để tìm resource thỏa mãn các điều kiện được cung cấp.                      |
| `getRelatedResource()` | Truy vấn database để tìm resource liên quan thông qua khóa tham chiếu.                       |
| `checkPermission()`    | Kiểm tra permission của người dùng trên resource dựa trên dữ liệu phân quyền trong database. |

Backend là nơi thực hiện kiểm tra quyền có tính bảo mật và quyết định cuối cùng đối với việc cho phép hoặc từ chối một request.

### Frontend

Trên Frontend, `PolicyResolver` sử dụng dữ liệu đã được cung cấp bởi các React Context thay vì truy vấn database.

Các nguồn dữ liệu chính bao gồm:

- **RolesContext:** Cung cấp thông tin role và permission của người dùng hiện tại.
- **ResourcesContext:** Cung cấp thông tin resource hiện tại và các dữ liệu resource đã được tải về.

| Method                 | Implementation                                                                    |
| ---------------------- | --------------------------------------------------------------------------------- |
| `findResource()`       | Tìm kiếm resource trong dữ liệu được cung cấp bởi `ResourcesContext`.             |
| `getRelatedResource()` | Tìm resource liên quan dựa trên dữ liệu resource có sẵn trong `ResourcesContext`. |
| `checkPermission()`    | Kiểm tra permission dựa trên thông tin role và permission từ `RolesContext`.      |

Frontend có thể không có đầy đủ dữ liệu resource như Backend. Vì vậy, kết quả kiểm tra policy trên Frontend chỉ phục vụ mục đích điều khiển giao diện và trải nghiệm người dùng, không thay thế việc kiểm tra quyền trên Backend.

#### ApiRolesGetter

Như đã giới thiệu ở phần đầu, ứng dụng web của RoxaVN được chia thành ba phần chính Admin Dashboard, Personal Profile, Custom Application. Mỗi phần có cơ chế quản lý quyền (role & permission) khác nhau, nhưng đều sử dụng chung kiến trúc `ApiRolesGetter` và `RolesContext` để quản lý quyền người dùng trên frontend.

##### 1. Admin Dashboard

Trong Admin Dashboard, khi người dùng truy cập, client sẽ tự động lấy toàn bộ danh sách `role` mà user đang có trong các module bằng component `ApiRolesGetter`.

```tsx
// Component ApiRolesGetter có nhiệm vụ lấy danh sách `role` của người dùng,
// sau đó lưu vào RolesContext để các component con có thể sử dụng lại.
<ApiRolesGetter api={authService.getUserModulesApi}>
  <AdminComponent />
</ApiRolesGetter>;
```

Sau khi `RolesContext` được khởi tạo, tất cả các trang hoặc component con có thể sử dụng các cơ chế kiểm tra quyền như:

```tsx
<IfCanAccessApi api={messageApi.create}>
  <CreateMessageButton />
</IfCanAccessApi>;
```

> ✅ **Lưu ý:**
> Trong Admin Dashboard, bạn không cần gọi lại API để lấy role của người dùng — vì `ApiRolesGetter` đã tự động xử lý điều này ngay từ đầu.

##### 2. Personal Profile và Custom Application

Đối với Personal Profile hoặc ứng dụng tuỳ chỉnh, quyền truy cập thường phụ thuộc vào **tài nguyên (resource)** cụ thể — ví dụ như `Channel`, `Project`, ...

Trong các trường hợp này, bạn cần đặt component `ApiRolesGetter` ở cấp phạm vi của đối tượng, để chỉ lấy các role có liên quan đến resource đó.

```tsx
<ApiRolesGetter
  api={authService.getUserRolesApi} // không yêu cầu set vì mặc định là authService.getUserRolesApi
  apiRequest={{ resourceType: resources.Channel.name, resourceTd: channel.id }}
>
  <ChannelDetail />
</ApiRolesGetter>;
```

- `resourceType`: tên của tài nguyên cần lấy quyền (ví dụ: `"channel"`).
- `resourceTd`: định danh cụ thể của tài nguyên (ví dụ: `channel.id = "1"`).

Sau đó `RolesContext` sẽ lưu role cho phạm vi này, toàn bộ các component con bên trong (như danh sách tin nhắn, hành động xoá, ghim, chỉnh sửa, v.v.) có thể sử dụng trực tiếp `IfCanAccessApi` để kiểm tra quyền.

##### 3. Cách hoạt động tổng quát

1. `ApiRolesGetter` gọi API lấy danh sách role tương ứng với **resourceType** và **resourceTd**.
2. Các role được lưu vào `RolesContext`.
3. `IfCanAccessApi` và `useAuthorization()` tự động đọc dữ liệu trong `RolesContext` để kiểm tra quyền truy cập.
4. Nếu người dùng không có quyền phù hợp, component sẽ không hiển thị.

#### ResourcesContext

Khi bạn sử dụng component `<ApiFetcher />`, sau khi client gọi API và nhận được dữ liệu, RoxaVN sẽ:

1. Lưu dữ liệu này vào `ResourcesContext` với resource tương ứng trong API.
2. Nếu dữ liệu là 1 danh sách các đối tượng thì lưu từng đối tượng với id của nó.
3. Khi `findResource()` được gọi, nó sẽ tự động lấy resource từ `ResourcesContext` để kiểm tra.

### Shared Policy

Nhờ sử dụng chung interface `PolicyResolver`, policy có thể được định nghĩa một lần và sử dụng trên cả Backend lẫn Frontend.

Ví dụ:

```ts
const workflowOwnerPolicy = async ({
  request,
  user,
  $resolver,
}: PolicyContext<{ workflowId: string }>) => {
  const workflow = await $resolver.getResource({
    resource: resources.Workflow,
    id: request.workflowId,
  });

  return !!workflow && workflow.createdBy === user?.id;
};
```

Policy trên không cần quan tâm:

- Backend lấy workflow từ database.
- Frontend lấy workflow từ `ResourcesContext`.
- Backend kiểm tra permission từ dữ liệu phân quyền trong database.
- Frontend kiểm tra permission từ `RolesContext`.

Việc lựa chọn nguồn dữ liệu và cách triển khai được xử lý bởi từng implementation của `PolicyResolver`.

### Những điểm cần lưu ý quan trọng

- **Backend is authoritative:** Backend luôn phải thực hiện kiểm tra quyền độc lập, không tin tưởng kết quả kiểm tra từ Frontend.
- **Frontend is context-dependent:** Kết quả kiểm tra phụ thuộc vào dữ liệu hiện có trong các Context. Nếu dữ liệu chưa được tải hoặc không khả dụng, policy có thể không đưa ra được kết quả chính xác.
- **Consistent API:** Cả hai môi trường phải tuân thủ cùng interface để đảm bảo policy có thể tái sử dụng.
- **No direct data access:** Policy không nên truy cập trực tiếp database hoặc React Context. Mọi thao tác truy xuất dữ liệu phải thông qua `$resolver`.
